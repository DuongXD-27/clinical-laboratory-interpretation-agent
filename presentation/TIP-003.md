## NO LAB VALUES THROUGH CHAT (Contractor decision D-9) — SAFETY CRITICAL

The Orchestrator MUST NEVER accept lab values, units, or indicator readings from the
chat message, and MUST NEVER construct analysis input by extracting numbers from
natural language.

Analysis is initiated ONLY through the existing endpoints:
  /analyze        — manual entry with input validation
  /ocr/confirm    — after HITL review

INT-01 ANALYZE_REPORT arriving via chat has exactly two outcomes:
  current_report_ref exists  -> return the existing analysis via get_my_report()
  no current_report_ref      -> status=needs_input, and suggested actions directing
                                the user to the manual-entry or upload flow

If the user types "my HbA1c is 7.2, is that bad?", you do NOT parse 7.2.
You return needs_input and point them at the input flow.

Reason: an LLM extracting values from prose must guess the unit, guess the canonical
analyte, and guess the reference context. Every one of those guesses would flow
straight into the deterministic medical pipeline with no validation in between.
This is the same failure class as OCR laundering (decision D-C).

## OCR STATE
- Read pending_ocr_review from the authoritative OCR workflow (see Q0-1).
  Never from the client.
- Never mutate HITL status from this layer.
- If the user asks to skip confirmation, in any phrasing, in any language:
  status=blocked, reason_code=OCR_REVIEW_REQUIRED, and offer the CONFIRM_OCR action.
- Manual validated input does NOT pass through the OCR gate.
